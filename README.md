# 회의록 요약 및 Action Items 추출 업무 자동화 프롬프트 패키지
본 문서는 업무 자동화 프롬프트 패키지의 최종 결과물로서 3종 모델 비교 보고서, 시스템 및 프롬프트 설계서, 10턴 대화 검증 로그, 그리고 운영 극대화를 위한 심층 인터뷰 내용을 단 하나의 문서로 가독성 있게 정리한 파일입니다.
---
## 1부. LLM 모델 비교·선정 보고서
### 1. 비교 목적
실제 비즈니스 환경에서 발생하는 다소 정돈되지 않은 '회의록 원문'을 입력받아, 정보 누락이나 환각(Hallucination) 없이 정확한 결정사항, 역할별 실행 파일(Action Items), 프로젝트 리스크 및 기한을 일목요연하게 요약·추출할 수 있는 최적의 LLM을 선정하고자 합니다.

## 2부. 시스템 설계 및 프롬프트 설계서
### 1. 문제 정의 및 타겟 사용자
* 업무 문제: 비정형 회의록에서 할 일(Action Items)이 누락/왜곡되거나, 정리자가 자의적으로 팩트를 지어내어 기록하는 문제를 해결하고자 함.
* 타겟 사용자: IT 테크 기업의 PM, 기획자, 개발 팀 리드.
* 입력 데이터 형태: 대화 덤프, 러프한 요약 메모, STT 한글 텍스트.
* 출력 규격: 핵심 결정사항, 역할별 Action Items, 리스크/후속 일정 템플릿.
### 2. 환각(Hallucination) 개념 정의 및 창의적 생성과의 구분 이유
* 환각의 정의: 대규모 언어 모델(LLM)이 입력값들을 통해 통계적으로 가장 그럴듯한 '다음 단어(토큰)'를 선택·예측하여 문장을 생성하는 확률적 구조로 동작하기 때문에, 주어진 입력 데이터에 없거나 사실 관계에 어긋나는 거짓 정보를 마치 확고한 사실인 양 자신 있게 답변하는 현상입니다.
* 창의적 생성과의 구분 사유: 소설, 마케팅 문구, 광고 카피 작성 등의 '창의적 생성(Creative Generation)' 분야에서는 모델의 무작위 확률 분산이 기발하고 유연한 결과물을 내는 가치로 작동하여 '환각'이 오류가 아닌 유용한 속성이 됩니다. 반면, 프로젝트 일정 조율, 규정 분석, 회의록 요약 등의 '업무 자동화 과업'은 단 하나의 날짜나 조건 오차가 사업 전체의 일정 파탄 또는 컴플라이언스 위반 리스크로 직결되는 영역입니다. 따라서 참/거짓 판별이 불가능한 창의적 생성과 달리, 실제 참인 명제가 존재하는 사실(Fact) 중심 업무에서는 환각을 '심각한 사실 오류'로 정의하고 엄격하게 검증 및 통제해야 합니다.

### 3. 프롬프트 구성 요소의 구조적 분리
이 시스템은 명확한 역할 정의와 재사용성을 위해 시스템 프롬프트, 유저 프롬프트 템플릿, 그리고 입력 데이터 템플릿으로 구조를 명확히 분리하여 설계되었습니다.
#### [1] 시스템 프롬프트 (System Prompt) - v2 최종본
```text
[Role]
당신은 10년 차 IT 테크니컬 PM 페르소나인 '에이든(Aiden)'입니다. 사실에 기반하여 회의록을 요약하고 리스크를 점검합니다.
[Mission]
제공된 회의록 텍스트를 분석하여 의사결정 사항을 요약하고, 담당자별 실행 과제(Action Items)를 매핑합니다.
[Reasoning & Processing Steps]
답변을 생성하기 전, 내부적으로 다음 3단계 과정을 거쳐 추론하십시오.
1단계 (정보 선별): 회의록 전체를 검토해 날짜(YYYY-MM-DD 형식 변환 고려), 인물의 역할, 명시적인 업무 지시 사항을 분류합니다.
2단계 (비교 및 검증): 대화 참여자들의 이름(김철수, 이영희 등)을 해당 직무 역할명(PM, FE 개발자, BE 개발자, 디자이너 등)으로 바르게 치환했는지 검증합니다. 회의록에 언급되지 않은 정보나 일정은 자의적으로 단정 짓지 않습니다.
3단계 (모호성 판별): 핵심 액션 아이템 중 기한이나 담당자가 빠진 사항이 있는지 파악하고, 만약 요약이 불가능할 정도로 핵심 정보가 모호한 경우 출력 양식을 생략하고 질문 리스트로 선회합니다.
[Constraint & Output Rules]
1. 최종 출력에는 1~2단계의 '생각 과정'이나 중간 메모를 노출하지 마십시오. 최종 답변은 오직 지정된 템플릿 형태로 요약된 팩트와 리스크만 깔끔하게 출력해야 합니다.
2. 날짜는 항상 YYYY-MM-DD 형식으로 기록하십시오. 상대적인 날짜(예: 내일, 사흘 뒤)는 회의 시점(기준일: 2026-06-06)을 바탕으로 날짜를 계산해 표기하십시오.
3. 사실, 수치, 규정에 대해 회의록 내용으로 증명되지 않는 사실은 절대 단정적인 어조로 적지 말고 "확인 필요"로 표기하십시오.

4부. 심층 인터뷰 및 운영 전략
Q1. 만약 비용 제약으로 '무료 모델만' 써야 한다면 품질을 유지하기 위해 프롬프트/프로세스를 어떻게 변경하겠습니까?
프롬프트 체이닝(Prompt Chaining) 프로세스 설계: 무료 모델(예: GPT-3.5 수준 또는 소형 오픈소스 모델)은 복잡하고 다단계의 명령(역할 변환 + 날짜 계산 + 요약 템플릿 완성)을 하나의 프롬프트 안에서 동시에 내릴 경우, 뒤쪽의 지시를 쉽게 잊거나 정확도가 급락합니다. 이를 보완하기 위해 작업을 단일 호출 단위로 나눕니다.
1단계: 원문의 대화 기록에서 모든 사람의 실명을 'PM, FE 개발자, BE 개발자, 디자이너'로 일차 치환시키는 변환 작업 수행.
2단계: 치환 완료된 텍스트를 입력으로 받아, 상대적인 기한 표현(예: 내일, 사흘 뒤)에 대해서만 기준일을 바탕으로 실제 날짜(YYYY-MM-DD)를 매핑하는 작업 수행.
3단계: 최종적으로 정제된 데이터를 요약 템플릿 양식에 맞추어 마크다운으로 렌더링.
Strict 구조 강제 및 One-shot 제약: 지시문 자체를 길고 복잡하게 나열하는 대신, 예시(Few-shot)의 텍스트가 지시문보다 잘 동작하므로 매우 짧은 입력에 대해 아주 이상적으로 작동한 1개 내지 2개의 One-shot 구조를 명확히 제시하여 모델이 생각 과정 없이 해당 예제를 형태 그대로 모방하도록 극도로 제한합니다.
Q2. 만약 업무 정책(규정/수치)이 자주 바뀐다면 환각을 줄이기 위한 시스템 운영 전략은 어떻게 됩니까?
동적 컨텍스트 인젝션 (Dynamic Context Injection): 시스템 프롬프트 내부에 고정된 형태의 규정이나 텍스트를 기재해 두면, 정책 변경 시 프롬프트 엔지니어링을 매번 다시 실행해야 합니다. 이를 피하기 위해 외부 DB나 사내 위키 API에서 매 실행 순간의 최신 가이드라인 규정을 불러와 유저 프롬프트 머리글에 [최신 정책 기준일: YYYY-MM-DD]와 함께 주입하는 동적 아키텍처를 도입합니다.
RAG (Retrieval-Augmented Generation) 시스템 구축 및 출처 인용 의무화: 규정 데이터베이스를 벡터화(Embedding)하여 사용자의 입력 혹은 업무 요약과 가장 관련성이 높은 상위 K개의 최신 규정 단락들을 검색(Retrieve)해 가져옵니다. 모델에게 "반드시 주입된 규정 단락 내에 명시된 범위에서만 답변하고, 해당 문장이 참조한 단락 번호(예: [규정 3조 2항])를 문장 끝에 반드시 표기할 것. 단락에 존재하지 않는 내용은 아는 지식을 사용하지 말고 무조건 '가이드라인에 명시되어 있지 않아 확인 불가능함'을 선언할 것"이라는 강한 Grounding 페널티를 부여하여 오정보 생성을 차단합니다.
Q3. 10턴 이상의 대화에서 문맥이 끊기는 문제가 생겼다면 이를 해결하기 위한 프롬프트 구조를 어떻게 개선하겠습니까?
세션 상태 요약본 누적 전달 (Rolling Summary Pattern): 대화가 거듭될수록 이전의 대화 내용 전체를 컨텍스트 윈도우에 밀어 넣는 방식은 토큰 비용을 높일 뿐 아니라 모델의 주의력(Attention)을 분산시켜 문맥 유지를 방해합니다. 따라서 대화가 5턴 이상 지속되면 이전 대화 기록 전체를 넣지 않고, 백그라운드에서 주기적으로 현재까지 합의된 팩트 리스트([최종 결정사항], [담당 역할별 할 일 기한], [보안 제약사항])의 상태 요약본을 갱신하여 시스템 프롬프트 바로 하단에 고정적으로 얹어서 모델로 전송합니다.
듀얼 에이전트(Dual-Agent) 상태 관리자 아키텍처 도입: 업무 자동화를 수행하는 메인 어시스턴트(Aiden) 외에, 사용자가 중간에 내린 변경 명령(예: "톤을 딱딱하게 바꿔줘", "마감일 연장해줘")만을 가로채어 세션의 제약조건 파일(JSON 형태의 State)을 실시간으로 갱신하는 '상태 관리자 모델'을 가볍게 앞단에 둡니다. 이 모델이 갱신한 JSON 상태 데이터를 메인 프롬프트의 지시조건 영역에 동적으로 덮어씌움으로써 대화 누적에 따른 성능 저하와 문맥 누락을 근본적으로 차단할 수 있습니다.
